와이어프레임에서 디자인까지

Cursor와 Figma MCP로 서비스 개요를 화면까지 옮기는 절차.

대상: 기획 · 디자인 · 에이전트 워크플로를 같이 쓰는 팀

Agenda

오늘 맞출 세 가지

01

기존 절차를 살린다

개요 → 다이어그램 → 와이어 → 테마·레퍼런스 디자인은 유지한다. 빠진 게이트만 끼운다.

02

도구를 단계에 묶는다

각 단계에서 Cursor가 쓰는 산출물과 Figma MCP 도구를 한 세트로 고정한다.

03

프롬프트 규약을 맞춘다

한 번에 앱 전체를 그리지 않는다. 인벤토리, 한 화면, 한 섹션 단위로 요청한다.

As-is

지금 팀이 쓰는 4단계

1

서비스 개요

목적, 타겟, 사용자 시나리오를 글로 고정한다.

2

다이어그램으로 재정리

Agent가 IA, Sequence 등으로 서비스를 한 번 더 구조화한다.

3

와이어프레임

화면 골격과 정보 배치를 그린다.

4

테마 후 디자인

4-1 App Theme(Primary Light/Dark, Mood). 4-2 레퍼런스 + 테마로 와이어를 입힌다.

방향은 맞다. 문제는 단계 사이가 비어 있고, Agent가 4번으로 바로 뛰어넘는 것이다.

Gaps

이 4단계에서 자주 빠지는 것

시작 전

  • 플랫폼·디바이스·기존 디자인 시스템·브랜드 제약
  • Figma 파일 분리(FigJam / Design)와 MCP 권한
  • 하지 않을 일(비목표)과 성공 기준

와이어 전

  • 화면 목록과 핵심 플로우 우선순위
  • Empty / Loading / Error / Permission 상태
  • IA를 마인드맵으로 요청하면 MCP가 거절한다

디자인 전

  • 레퍼런스가 테마보다 뒤에 오면 Primary만 정해진다
  • 컬러만 있고 타이포·간격·라디우스·엘리베이션이 없다
  • 버튼·인풋·리스트를 안 만들고 화면부터 칠한다

디자인 후

  • 사람 리뷰 없이 다음 화면으로 진행
  • 다크모드를 복제 프레임으로 그려 토큰이 갈라진다
  • 구현 핸드오프와 프로토타입 연결이 없다

Principles

보완할 때 지키는 네 규칙

A

피델리티를 건너뛰지 않는다

예쁜 화면이 틀린 구조면 수정 비용이 더 크다. 개요·IA·와이어가 통과하기 전에 컬러를 넣지 않는다.

B

사람 게이트를 단계 사이에 둔다

Agent는 초안을 만든다. IA/와이어와 테마/컴포넌트에서 사람이 한 번씩 멈춘다.

C

토큰과 컴포넌트가 화면보다 앞선다

hex를 화면에 박지 않는다. Light/Dark는 변수 모드다. 반복 UI는 로컬 컴포넌트 먼저.

D

MCP는 작게, 같은 파일을 재사용한다

한 프롬프트에 앱 전체를 넣지 않는다. 다이어그램을 고칠 때도 새 FigJam을 만들지 않는다.

정립한 8단계

P2IA · 다이어그램사이트맵, 시퀀스, 상태
P3화면 인벤토리화면 목록, 우선순위, 상태
P4와이어프레임그레이스케일, 디바이스 프레임

P1 · Brief

서비스 개요 — 기존 1단계 보강

이미 하던 것

  • 목적
  • 타겟
  • 사용자 시나리오

꼭 추가할 것

  • 한 줄 문제 정의와 하지 않을 일
  • 핵심 과업 3개(이 앱에서 반드시 끝나는 일)
  • 성공을 무엇으로 볼지(정성 기준도 가능)
  • 레퍼런스 URL 3~5개와 “가져올 점 / 버릴 점”

레퍼런스는 테마 단계가 아니라 개요에 붙인다. 색깔을 고르기 전에 “밀도, 위계, 무드”를 말로 고정한다.

P2 · How

다이어그램은 이렇게 요청한다

brief.md를 읽고 아래만 만들어.
1) 사이트맵을 Mermaid flowchart로. 깊이는 3단.
2) 핵심 시나리오 1개의 sequenceDiagram.
3) 로그인~권한 상태 diagram.
generate_diagram으로 FigJam에 그려.
이미 보드가 있으면 같은 fileKey에 이어서 넣어.
노드를 창작하지 마. brief에 없는 기능은 빈칸으로 표시해.

Agent가 기능을 창작하지 않게

  • 없는 기능은 그리지 말고 표시만
  • 이모지, HTML 라벨, \n 금지(도구가 거절)
  • 같은 서비스를 고칠 때는 파일 재사용
  • 두 번 그려도 만족 못 하면 사람이 FigJam에서 고친다

P3 · Inventory

화면을 세기 전에 그리지 않는다

화면 목록 표

ID · 화면 이름 · 진입 경로 · 핵심 과업 · 우선순위(P0/P1/P2) · 필요 상태

상태 세트(화면마다)

Default, Empty, Loading, Error, Success, Permission denied. 해당 없으면 N/A.

이번 스프린트 범위

P0 화면만 와이어한다. “있으면 좋은 설정 탭”은 목록에만 남긴다.

Cursor 산출물

screens.md 표. Figma Cover 페이지에 같은 표를 요약 프레임으로 옮겨도 된다.

P4 · Wireframes

와이어는 회색으로만

해야 할 일

  • 기준 디바이스 프레임
  • Auto Layout, 실제에 가까운 카피
  • 내비·탭바·제스처 영역
  • 화면당 골격 한 세트

하지 말 일

  • 브랜드 컬러, 그라디언트, 일러스트
  • 한 프롬프트에 12화면
  • Lorem ipsum으로 높이 속이기
  • 절대좌표로 박스 쌓기

MCP 순서

  • use_figma로 페이지·프레임
  • 화면 래퍼 먼저, 섹션은 그 안
  • 섹션마다 get_screenshot
  • 잘린 텍스트·겹침만 고친다
01 Wireframes 페이지에 P0 화면만 그려.
회색(#111/#666/#DDD)만 사용. 컬러·그림자·이미지 금지.
각 화면은 디바이스 프레임 하나. 래퍼를 먼저 만들고 섹션은 그 안에.
한 호출에 섹션 하나. 끝나면 get_screenshot으로 겹침·잘림을 고친 뒤 다음 화면.

G1 · Gate

컬러 전에 사람이 보는 질문

  • 핵심 과업 3개가 화면 목록에 있는가
  • 시퀀스의 모든 hop이 화면 ID와 맞는가
  • Empty/Error를 어디로 보낼지 정했는가
  • 이번 범위 밖 화면을 와이어에 몰래 넣지 않았는가
  • 카피만 읽어도 위계가 보이는가

통과 조건

기획 또는 정한 리뷰어 한 명이 brief.md에 “G1 pass”와 고친 점을 한 줄 남긴다. 그 전에는 P5를 시작하지 않는다.

Agent에게 “괜찮으면 디자인까지”라고 쓰지 않는다. 게이트를 프롬프트에 명시한다.

P5 · Theme

테마는 Primary 한 색이 아니다

기존 4-1을 이렇게 넓힌다

  • 레퍼런스 3~5장을 Theme 페이지에 붙인다
  • 무드 키워드 4개(예: quiet, dense, warm, trustworthy)
  • Primitives: brand, gray ramp, danger/success/warning
  • Semantic: bg, surface, text, border, accent
  • Type scale, space/4, radius, elevation
  • Light / Dark는 같은 컬렉션의 모드

MCP

  • 레퍼런스 이미지: upload_assets 또는 파일에 붙여 넣은 뒤 해시 복사
  • 변수·모드는 use_figma + 라이브러리 스킬 순서(토큰 → 스타일)
  • 변수마다 scope를 지정. ALL_SCOPES 금지
  • 이미 팀 라이브러리가 있으면 get_libraries → search_design_system이 먼저

P6 · Components

화면보다 원자를 먼저 만든다

최소 세트

Button, Text field, List row, Nav/Tab bar, Card, Toast/Banner, Empty state, Icon slot

Variant

size, hierarchy(primary/secondary/ghost), state(default/hover/disabled/error), Light/Dark는 모드로

규칙

색·간격은 변수 바인딩. 아이콘은 SVG import. 회전한 선으로 아이콘을 재구성하지 않는다.

02 Theme 변수를 쓰고 03 Components에 최소 세트를 만들어.
색은 hex 하드코딩 금지. 바인딩만.
화면은 아직 그리지 마. 컴포넌트 페이지를 get_screenshot으로 보여준 뒤 멈춰.

P7 · High-fi

와이어를 입히되, 덮어쓰지 않는다

  • 04 Screens에 P0부터. 01 Wire는 그대로 두고 페이지를 나눈다
  • 컴포넌트 인스턴스만 조립. 박스 재발명 금지
  • 한 화면 = 래퍼 생성 → 섹션 단위 use_figma → 섹션 스크린샷
  • 웹이고 라이브 URL이 있으면 generate_figma_design 캡처와 병행 가능. 캡처는 참고 후 삭제
  • Dark는 프레임 복제가 아니라 모드 전환으로 검증

한 번에 실패하는 요청

“레퍼런스처럼 앱 전체를 예쁘게 그려줘.” 결과는 토큰 없는 그림이다. 화면 ID, 쓸 컴포넌트, Light/Dark 중 어느 모드인지를 적는다.

핵심 시퀀스 1개를 연결한다. 모든 화면을 플로우로 묶지 않는다.

구현이 필요할 때

get_design_context는 참고 코드다. 프로젝트 컴포넌트에 맞게 옮긴다. Code Connect는 라이브러리가 안정된 뒤.

Prompts

모든 단계에 넣는 네 줄

역할: Cursor + Figma MCP로 [P?]만 수행.
입력: brief.md, screens.md, Figma fileKey [ ], 지금 페이지 [ ].
범위: [화면 ID 또는 컴포넌트]. 다음 단계로 넘어가지 마.
제약: 없는 기능을 창작하지 마. hex 하드코딩 금지(P5+).
완료: 만든 node id / file URL과 get_screenshot 결과를 보고하고 멈춰.

전체 치트시트는 같은 폴더 prompts.md.

Anti-patterns

이렇게 시키면 실패한다

  • “Linear 느낌으로 온보딩부터 설정까지”
  • 다이어그램을 돌릴 때마다 새 보드
  • 다크모드 화면을 복제해서 색만 반전
  • 아이콘을 선·원으로 다시 그림
  • 에러 없이 끝난 스크립트를 성공으로 간주(폰트가 Inter로 바뀌어도 성공으로 보임)
  • Figma 파일 없이 로컬 HTML을 디자인으로 대체하고 끝
  • 화면 ID와 레퍼런스 “가져올 점”을 명시
  • 같은 fileKey에 이어서 생성
  • 변수 모드로 Light/Dark
  • 코드 또는 키트에서 SVG import
  • 섹션 스크린샷으로 잘림·폰트·플레이스홀더를 사람이 확인
  • 산출물은 Figma. HTML PT는 이 프로세스 문서용

Checklist

파일럿 한 서비스에 적용할 때

P0 MCP 로그인, Design 파일, 페이지 5개, 플랫폼·프레임 기록

P1 목적/타겟/시나리오 + 비목표 + 과업 3 + 레퍼런스 3

P2 사이트맵 플로차트, 핵심 시퀀스 1, 상태 1. 같은 FigJam

P3 화면 표와 상태. P0 범위만 별도 표시

G1 사람 한 줄. 컬러 시작 금지

P4 회색 와이어, 섹션 단위, 스크린샷

P5 레퍼런스 보드, semantic 토큰, Light/Dark 모드

P6 최소 컴포넌트, 변수 바인딩, 페이지 리뷰 후 정지

P7 P0 화면 하이파이, 인스턴스 조립, G2

닫기 시퀀스 1개 프로토. 구현은 필요할 때만

Compare

Claude Design과 자리가 다르다

Cursor + Figma MCP

진실의 원천은 Figma 파일. 개요→IA→회색 와이어→토큰→인스턴스. G1 전에 색을 넣지 않는다.

Claude Design

설명하면 초안이 나온다. 대화·슬라이더·직접 편집. 산출물은 프로토·덱·HTML이고 Claude Code로 넘긴다.

Claude Design 커넥터는 Adobe, Canva, Miro, Lovable, Vercel 등. Figma는 그 목록에 없다. Figma로 심는 작업은 우리 프로세스가 맡는다.

Designer

디자이너

Figma MCP가 앞설 때

  • 변수·모드·컴포넌트가 팀 파일에 남는다
  • 기존 리뷰, 라이브러리, Dev Mode
  • 예쁜 오답을 G1이 늦춘다

부담

  • 방향 12개를 뽑는 속도는 느리다
  • Agent 트리는 스크린샷 보정이 필요하다
  • 클릭감은 P7 전엔 약하다

Claude Design이 앞설 때

  • 방향 탐색, 브랜드 초안
  • 공유용 인터랙티브 프로토 (PR 없이)
  • 덱·마케팅 에셋까지 한곳

부담

  • Figma 라이브 인스턴스가 아니다
  • 확정 후 Figma에 다시 심는 비용
  • 멀티플레이어·버전은 Figma가 강하다

PM

기획자

Cursor + Figma MCP

장점: brief, 화면 표, Empty/Error, G1, FigJam. 이해관계자가 이미 Figma를 본다.

단점: 회의 중 클릭 데모까지 멀다. MCP 규약이 있다. 그레이 와이어는 ‘덜 된 것’으로 보일 수 있다.

Claude Design

장점: 그 자리 데모, 조직 링크, 덱. Figma를 못 다뤄도 시나리오를 보여줄 수 있다.

단점: 예쁜 초안이 결정처럼 보인다. 상태·우선순위 표는 안 생긴다. G1을 건너뛰기 쉽다.

Eng

개발자

Cursor + Figma MCP

장점: Figma 스펙, Code Connect, 토큰 모드, 네이티브 앱, Cursor 한 환경.

단점: 디자인이 코드가 아니다. 더러운 노드 트리, 인터랙션 검증은 별도.

Claude Design

장점: 프로토가 이미 돌아간다. Claude Code가 스크린샷부터 시작하지 않는다. 스파이크가 짧다.

단점: 프로토 코드 ≠ 제품 레포일 수 있다. 토큰이 세 곳에 생긴다. 한도를 채팅·코드와 나눈다.

Together

같이 쓰는 순서

  1. 기획이 시나리오를 적는다 (P1, 도구 무관).
  2. 방향이 여러 개면 Claude Design에서 2~3안을 클릭해 본다.
  3. 고른 안을 레퍼런스로 Cursor Skill P2–G1에 넣는다. 와이어는 회색.
  4. G1 뒤 Figma에 토큰·컴포넌트·하이파이.
  5. 제품 구현의 SoR은 하나. 웹 스파이크는 Claude Design, 장기 스펙은 Figma.

자세한 표는 compare-claude-design.md.
